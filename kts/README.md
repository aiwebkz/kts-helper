# kts-helper — macOS и Windows

Модифицированный RustDesk 1.5.3. Основа зафиксирована на commit
`95cca3f661f635b3cc85c04935fe8d96d8f432ef`, подмодуль `hbb_common` —
`fae47e024dd83cef6aaecde0aa7d11731df11649`.
Upstream: https://github.com/rustdesk/rustdesk.

## Что подготовлено

- Имя `kts-helper`, собственные иконки Windows/macOS, логотипы для светлой и тёмной темы,
  значок трея и бирюзовые акценты.
- Отдельный bundle ID `org.kts.helper`; исходный Apple Development Team удалён из проекта.
  Перед подписанием замените bundle ID на идентификатор своей организации.
- Настройки своего ID-сервера, relay и публичного ключа встроены в клиент через
  `OVERWRITE_SETTINGS`; обычные настройки пользователя их не заменяют.
- По умолчанию входящий доступ требует нажатия «Принять». Режим допуска можно изменить
  в штатных настройках безопасности. Общего пароля или скрытого доступа в форке нет.
- Проверка штатных обновлений RustDesk и автоматическое обновление отключены.
- Ручной GitHub Actions workflow для Windows x64/ARM64 и macOS Intel/Apple Silicon.
  Выход: самораспаковывающийся Windows EXE с установкой, macOS DMG, исходники и SHA256.
- Docker Compose для своего сервера RustDesk OSS, с общей постоянной папкой ключей.

Сервер развёрнут на Ubuntu VPS и доступен через Tailscale: `100.90.108.74`.
SSH: `ssh dbykov@138.201.183.179 -p 52022`. Оба контейнера запущены, ключ сервера
встроен в `config.json`. Порты firewall открыты только на интерфейсе `tailscale0`.
Для работы оба клиента должны войти в ту же сеть Tailscale; её ACL должны разрешать
им доступ к TCP 21115–21117 и UDP 21116 сервера. Напрямую из интернета сервер недоступен.

Нативные клиенты и соединение двух машин пока не проверены; установщики собираются
отдельно через GitHub Actions. См. `server/DEPLOYMENT.md` для обслуживания сервера.

## 1. Поднять сервер на Linux VPS

Нужны Linux, Docker Engine с Compose v2 и публичный IP. Создайте DNS A-запись, например
`remote.your-domain.ru`, указывающую на VPS. Не включайте HTTP proxy/CDN для этой записи:
соединения используют TCP/UDP, а не обычный HTTPS.

Скопируйте `kts/server` на VPS. Затем из этой папки:

```sh
cp .env.example .env
# В .env задайте RELAY_HOST=remote.your-domain.ru (без протокола и порта).
mkdir -p data
chmod 700 data
docker compose config
sh start.sh
docker compose ps
docker compose logs --tail=50 hbbs hbbr
cat data/id_ed25519.pub
```

Compose использует host network и предназначен для Linux VPS. `hbbs` сначала создаёт
ключи; `start.sh` запускает `hbbr` после появления ключей и использует ту же пару.
Образ зафиксирован на `rustdesk/rustdesk-server:1.1.16`.

Откройте на firewall VPS и в firewall провайдера TCP **21115–21117**, UDP **21116**.
Для WebSocket при необходимости дополнительно TCP **21118–21119**.
TCP 21114 относится к Pro API; для этой OSS-конфигурации не нужен.
Если VPS за NAT, перенаправьте те же порты на него.

Скопируйте **только** `id_ed25519.pub` в конфигурацию клиента.
Приватный `id_ed25519` остаётся на сервере; делайте резервную копию всей папки `data`.
Оба сервиса запускаются с `-k _`, требуя соответствующий публичный ключ клиента.
Публичный ключ идентифицирует сервер, но не заменяет подтверждение доступа к компьютеру.

## 2. Настроить клиент

Из корня репозитория `rustdesk` отредактируйте `kts/config.json`:

```json
{
  "app_name": "kts-helper",
  "bundle_id": "org.kts.helper",
  "accent": "167D8D",
  "id_server": "remote.your-domain.ru:21116",
  "relay_server": "remote.your-domain.ru:21117",
  "public_key": "СОДЕРЖИМОЕ_id_ed25519.pub"
}
```

```sh
python3 kts/configure.py --check
python3 kts/configure.py
```

В текущей конфигурации уже указаны адрес Tailscale и публичный ключ развёрнутого сервера. `configure.py --preview` позволяет
подготовить оформление без сервера, подставляет несуществующий `unconfigured.invalid`
и добавляет `compile_error!` для release. Обычный запуск `configure.py` с корректными
настройками снимает эту блокировку. Не удаляйте её вручную.

`app_name` уже применён как `kts-helper`. Перед дальнейшим переименованием или сменой
цветовой схемы обновите соответствующие применённые ресурсы: конфигуратор рассчитан
на повторное применение текущего бренда и обновление серверных параметров, а не на
отмену произвольных переименований. Названия Rust-библиотек, FFI и протокола сохранены
для совместимости с upstream. Swift module также оставлен `RustDesk` для ссылок XIB.

Для повторной генерации иконок после изменения дизайна:

```sh
python3 -m venv kts/.venv
kts/.venv/bin/pip install -r kts/requirements-tools.txt
kts/.venv/bin/python kts/make_icons.py
```

Исходный знак: `kts/branding/icon.svg`, генератор растровых ресурсов: `make_icons.py`.
PNG, ICO и ICNS уже созданы и должны храниться в Git.

## 3. Создать свой репозиторий и собрать

Папка `rustdesk` — самостоятельный Git-репозиторий с веткой `kts-helper`.
Удалённый `upstream` ссылается на оригинал, `origin` — на
https://github.com/aiwebkz/kts-helper. Ветка продукта — `kts-helper`.
Для переноса в другую организацию измените `origin`; перед отправкой проверьте diff.

```sh
git add .
git commit -m "Prepare kts-helper desktop fork"
# При переносе: git remote set-url origin https://github.com/YOUR_ORG/kts-helper.git
git push -u origin kts-helper
```

В GitHub откройте **Actions → Build kts-helper desktop → Run workflow** и выберите
ветку `kts-helper`. Workflow запускается только вручную и публикует результаты в
Artifacts запуска, без GitHub Release. Все необходимые reusable workflows находятся
в репозитории. Он сохраняет настройки компиляторов/Flutter/vcpkg из upstream 1.5.3.

Проверка конфигурации выполняется до тяжёлых сборок. Если сервер или ключ отсутствует,
сборка остановится в `validate`. Для первой компиляции понадобятся загрузка зависимостей,
время и доступные GitHub runner minutes; ARM64 runners могут зависеть от доступности
тарифа и платформы. Проверки подписания в этом workflow не выполняются.

В каждом наборе артефактов ожидаются:

- `kts-helper-1.5.3-<arch>-install.exe` для Windows либо `kts-helper-1.5.3-<arch>.dmg` для Mac;
- `kts-helper-source.tar.gz` с модифицированным кодом и подмодулем;
- `SHA256SUMS`.

Windows-пакет первой версии не включает дополнительно скачиваемые драйверы виртуального
монитора и удалённого принтера. Основные функции экрана, ввода и передачи файлов остаются
в штатном ядре. MSI пока не добавлен; используется встроенная установка из EXE.

## Подпись и приёмка

Этот workflow собирает тестовые пакеты без подписи издателя. Для распространения
понадобятся собственные сертификаты Windows и Apple Developer ID, подпись всех вложенных
компонентов Mac, нотариализация и stapling. Приватные сертификаты и пароли храните в
Secrets CI, не в `config.json`. Штатные upstream workflows подписания сохранены как
справочный материал; `kts-build.yml` не обращается к сервисам подписи RustDesk.

Перед распространением выполните проверку на двух реальных машинах:

1. Mac → Windows и Windows → Mac: подключение по ID, принятие и отклонение запроса,
   управление мышью/клавиатурой, русский текст, буфер обмена и передача файла.
2. На Mac выдайте приложению разрешения «Запись экрана», «Универсальный доступ» и,
   если запрошено, «Мониторинг ввода», затем перезапустите его.
3. Windows: установка/удаление, работа службы после перезагрузки, UAC; Mac:
   запуск из `/Applications/kts-helper.app` и установка службы.
4. Две разные сети: прямое подключение и принудительный relay. Убедитесь по журналам,
   что используются ваши `hbbs`/`hbbr`; проверьте отказ при неверном публичном ключе.
5. Установите рядом обычный RustDesk: настройки, ID, службы и разрешения должны
   оставаться раздельными. Для этого проверяйте и отдельный bundle ID Mac.

## Проверки и изменения относительно upstream

```sh
python3 -m unittest discover -s kts/tests -v
python3 kts/configure.py --check
git diff --check
```

Регрессионная поверхность намеренно ограничена:

- `src/common.rs` и `src/lib.rs`: два вызова и подключение нового `src/kts.rs`, чтобы
  применить имя/сервер до чтения профиля во всех процессах, включая службу и Flutter FFI.
- `flutter/lib/common.dart`, `desktop_home_page.dart` и графические ресурсы: цвета и бренд.
- Конфигурация Xcode, схема и `build.py`: отдельный bundle ID, имя `.app` и путь службы.
- Windows `Runner.rc`, иконки и метаданные portable packer: название и значки EXE.
- `.gitignore`: сохранение своих ресурсов, исключение локальных ключей/данных сервера.

Сетевой протокол, кодеки, захват экрана, ввод, криптография и подмодуль не изменялись.
Клиенты сохраняют штатные возможности прямого доступа; встроенный сервер — настройка
инфраструктуры ID/relay, а не запрет всех альтернативных способов соединения.

## Лицензия и сопровождение

Сохранены `LICENCE`, исходные copyright notices и ссылка на RustDesk в интерфейсе.
Модификации описаны в `kts/NOTICE.txt`. Распространяйте исходный архив вместе с каждым
пакетом; GitHub Actions Artifacts имеют ограниченный срок хранения и не подходят как
единственный долгосрочный источник для получателей. При создании страницы загрузки
разместите рядом соответствующий архив исходников и текст AGPL-3.0.

Для обновления сначала изучайте diff следующего стабильного тега, переносите небольшой
набор изменений и заново проверяйте нативные сборки. `kts-build.yml` получен из upstream
workflow скриптом `kts/generate_workflow.py`; оригинальный `flutter-build.yml` не менялся.
Не запускайте старые nightly/publish workflows для выпуска kts-helper.
